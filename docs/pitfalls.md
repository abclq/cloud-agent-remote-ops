# 🕳 踩过的坑

> 全是真事。**每一条都让系统在某一刻失效过。**

---

## 坑 1：黑名单按字面列，漏了同义写法

**现象**：护栏测试时 `rm -rf /` 拦住了，但 `systemctl reboot` **过了**。

**原因**：黑名单里写的是 `reboot`（裸命令），忘了 `systemctl reboot` 也能重启。

**修**：按**语义**列，不按命令名列。

```bash
systemctl\s+(reboot|poweroff|halt|suspend|hibernate|kexec)
kill\s+-1\b
killall5
```

**教训**：写完黑名单，**逐条问自己"还有什么写法能达到同样效果"**。

## 坑 2：`authorized_keys` 是受保护文件，改不了

**现象**：想改 `command=` 指向的路径，工具直接拒绝：

```
Write denied: '~/.ssh/authorized_keys' is a protected system/credential file.
```

**这是对的** —— 那个文件确实该被保护。

**替代做法：转发壳**（只适合**还没开 `exec`** 的阶段）。把 `command=` 已经指向的那个**普通文件**改成转发：

```bash
#!/usr/bin/env bash
if [ -z "${SSH_ORIGINAL_COMMAND:-}" ]; then
    exec /path/to/old-behavior.sh          # 向后兼容
fi
exec /usr/local/bin/agent-entry.sh "$SSH_ORIGINAL_COMMAND"
```

**好处**：不碰 `authorized_keys`、不 reload sshd、老调用方不受影响。

**⚠️ 但**：如果那个壳归对面所有，**它也能改这个壳**。
所以壳里**不能放护栏** —— 护栏必须在 root 拥有的脚本里。

**教训**：受保护文件别硬绕。真要改入口，**让机主用 root 改 `ForceCommand`**；
转发壳只是只读阶段的过渡，开 `exec` 前必须拆掉，否则它能改壳 = 改入口。

## 坑 3：以为"发出去 = 人会看到"

**现象**：用邮件派活，跑通了，也真的回信了。后来发现对面 AI **根本没读**。

**原因**：翻它的会话记录才看到：

```
15:12:42  用户:  看看邮箱
15:14:10  AI:    有一封要处理：本机 23:05 发来的邮件…
```

**它是被问了才去读的。** 邮件**不会唤醒**它。

**教训**：区分**推送**（push）和**拉取**（poll）。

| 推送 | 拉取 |
|---|---|
| IM 消息、手机推送 | 邮件、RSS、文件 |
| 会主动响 | 等下次被想起来 |

**做实时派活/告警，必须用推送通道。**

## 坑 4：脚本静默失败，几天没人知道

**现象**：哨兵连续几天**什么都没报** —— 看起来"一切正常"。

**真相**：哨兵的邮件脚本 Gmail 调用失败后 **`exit 0` 了**。
于是"没消息"= "没故障"，实际上"哨兵死了"。

**修**：

1. 成功 → 写**心跳文件**
2. 失败 → **非零退出 + 写日志**
3. 另起一个检查：心跳文件超过 N 小时没更新 → 报警

**教训**：**静默失败是最危险的失败。**

> 任何脚本都要问：如果它今天什么都没做，有人会发现吗？

## 坑 5：告警风暴

**现象**：同一个问题每 10 分钟报一次，一天 144 条。

**结果**：开始无视告警 → **真故障也漏了**。

**修**：指纹去重。

```python
key = sha256("\n".join(sorted(f"{p['kind']}:{p['name']}" for p in problems)))
if key == last_key and state == last_state:
    return   # 闭嘴
```

⚠️ **别把 `checked_at` 算进指纹** —— 那样每次都不一样，等于没去重。

**教训**：**告警的价值 = 信噪比**，不是数量。

## 坑 6：`set -u` 让本地测试崩

**现象**：脚本在 SSH 里跑得好好的，本地一测就崩。

**原因**：

```bash
log() { echo "${SSH_CLIENT%% *}"; }   # SSH_CLIENT 只在 sshd 会话里有
```

`set -u` 下，本地跑时 `SSH_CLIENT` 未定义 → 直接退出。

**修**：

```bash
local from="${SSH_CLIENT:-local}"
```

**教训**：**入口脚本一定要能在本地测**。不能本地测 = 每次改都要走公网，效率极低。

---

## 坑 7：`exec "命令"` 带引号被误判

**现象**：`exec "df -h"`（带引号）被当成命令名 `"df` + 参数，或者元字符检查误伤。

**修**：先**去掉外层引号**再解析。

**教训**：参数从 SSH 过来时，**引号状态是不确定的**。别假设。

## 坑 8：护栏归被约束者所有 🔴

**现象**（最严重的一个）：入口脚本是 `user:user`，而对面**有写权限**。

→ 它能 `exec` 改掉入口脚本 → **改掉自己的护栏**。

**修**：

```bash
sudo install -o root -g root -m 755 agent-entry.sh /usr/local/bin/
```

**教训**：**护栏不能由被约束者持有。** 这是整个项目的核心原则。

**推论**：开写权限之前，必须审[提权链](privilege-audit.md)。

## 坑 9：消息里的反引号让发送脚本崩

**现象**：发送脚本在处理含反引号的文本时直接崩。

**修**：发之前检查。

```bash
if printf '%s' "$MSG" | grep -q '`'; then
    echo "🔴 含反引号，先换掉"; exit 1
fi
```

**教训**：**通道本身有输入限制，要先摸清楚。** 别等它崩了才知道。

## 坑 10：代理协议的兼容问题

**现象**：脚本用 `socks5://` 代理时崩，报 `Invalid URL protocol`。

**原因**：运行时（Node 某些版本）的代理实现**只认 `http://`**，不认 `socks5://`。

**修**：

```bash
unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY all_proxy ALL_PROXY
export HTTPS_PROXY=http://127.0.0.1:10809    # 换 http 代理
```

**教训**：**代理链上每一跳的协议支持都要实测。** 文档说支持 ≠ 你的版本支持。

---

## 坑 11：`gh` 走 http 代理 TLS 超时

**现象**：`gh repo deploy-key add` 走 `HTTPS_PROXY=http://127.0.0.1:10809` 报
`TLS handshake timeout`。

**修**：换 SOCKS5。

```bash
export HTTPS_PROXY=socks5h://127.0.0.1:10808   # 注意 socks5h
```

**教训**：**同一个机器上不同工具可能要不同代理协议。** 撞超时先换协议，别急着怀疑凭证。

## 坑 12：同一把 deploy key 挂不到两个仓库

**现象**：给第二个仓库加同一把公钥，失败。

**原因**：**GitHub 不允许同一把公钥挂在多个仓库上**（会报 `key is already in use`）。

**修**：**让对面自己生成一把新的**，只把**公钥**给你。

```bash
# 在对面机器上（私钥不出它的沙盒）
ssh-keygen -t ed25519 -C "repo-name" -f ~/.ssh/id_repo -N ""
cat ~/.ssh/id_repo.pub
```

**教训**：**公钥可以随便传，私钥永远不要经过任何中间通道。**

⚠️ 沙盒里的私钥是半公开的（见[威胁模型](threat-model.md)）—— 给它的 deploy key **只勾只读**。
GitHub 的 deploy key 一旦勾了 write，就是整仓库、所有分支的写权限，没法限到某个分支。

## 坑 13：`--user` 服务和系统服务搞混

**现象**：提权链审查时漏了一处，因为没分清 `systemctl --user` 和 `systemctl`。

**区别**：

| | 谁跑 | 它能改吗 | 要审吗 |
|---|---|---|---|
| `systemctl --user` | 它自己 | ✅ 能改 | ❌ 不用（那是它的权限范围） |
| `systemctl` | root | ❌ 不能改 | ✅ **要审** |

**教训**：审查时**明确问"这是谁的权限"**，别看到 `systemctl` 就当 root。

## 坑 14：`sshd -t` 没跑就 reload

**现象**（差点）：改 `sshd_config` 后直接 reload。如果配置有语法错，sshd 起不来 →
**把自己关在外面**。

**修**：

```bash
sudo sshd -t && sudo systemctl reload ssh
```

**外加**：reload 前**先开另一个 SSH 连接**（万一断了还能救）。

**教训**：**任何"能把自己关在门外"的改动，都要留后门。**

---

## 坑 15：退出码被 `echo` 吃掉

**现象**：`exec` 动作的退出码**永远报 0** —— 连 `exec false` 和 `exec exit 7` 都报 0。

**原因**：

```bash
bash -c "$cmd" 2>&1
echo
echo "── exec 退出码：$? ──"     # ← 这里的 $? 已经是 echo 自己的了
```

`$?` 只保留**上一条命令**的状态。中间插了个 `echo`，就把它覆盖成 0 了。

**修**：

```bash
local rc=0
bash -c "$cmd" 2>&1 || rc=$?    # 立刻存下来
echo
echo "── exec 退出码：$rc ──"
return "$rc"                     # 顺手让脚本退出码也跟上
```

**为什么这个 bug 特别值得记**：

它对**人**没影响（人会看输出内容），但对**对面那个 AI** 是致命的 ——
它的工作流是「修 → 看退出码 → 判断修好没」。退出码恒 0，等于**它永远以为修好了**。

**是它自己测出来报给我们的** —— 我们自测时没发现，因为人眼看输出觉得"挺正常的"。

**教训**：

1. **`$?` 要立刻取**，中间别插任何命令（连 `echo` 都不行）
2. **自测要站在对面 AI 的用法上测** —— 它靠什么判断，你就测什么
3. **退出码要能区分「被拒绝」和「命令失败」**（我们用 `126` 表示拒绝，见 [动作参考](actions.md)）

## 坑 16：修复脚本读的是**过期快照**

**现象**：停掉一个被监控的服务 → `verify` 正确报出故障 → 跑 `fix` → **服务还是死的**。

**原因**：`fix` 调的 `autofix.py` 读的是 `watcher_status.json` ——
而这个快照由另一个服务**每 5 分钟**刷一次。`verify` 是实时算的，`autofix` 是读快照的。
两者**数据源不一致** → 刚挂的服务，autofix 根本不知道。

**修**：`fix` 先刷新快照，再调 autofix：

```bash
python3 tasks-status.py --json > "$CACHE.tmp" || true
# 校验是合法 JSON 再原子替换
python3 -c "import json,sys; json.load(open(sys.argv[1]))" "$CACHE.tmp" && mv "$CACHE.tmp" "$CACHE"
```

**教训**：**检测和修复必须看同一份数据**。差一个缓存，修复就是"修了个寂寞"。

## 坑 17：`tasks-status.py` 的退出码被当成失败

**现象**：修好坑 16 后，日志里报「快照刷新失败」，但快照其实刷成功了。

**原因**：

```bash
if python3 tasks-status.py --json > "$CACHE.tmp"; then   # ← 错
```

`tasks-status.py` **在「有故障」时退出码本来就是 2** —— 这是它设计好的语义
（0 正常 / 1 定时任务问题 / 2 常驻服务问题）。
所以"有故障"≠"刷新失败"。

**修**：**别拿退出码判断成败，校验输出内容**（是不是合法 JSON）。

**教训**：**退出码是语义，不是成败**。自己设计的退出码，自己要在调用方正确解读 ——
否则同一个坑会在两个地方各踩一次。

## 坑 18：`systemctl stop` 原本是放行的

**现象**：护栏测试时发现 `exec systemctl --user stop <网关服务>` **被放行了**。
（那次只是碰巧失败，因为写的是 `--user`，而网关是系统级单元。）

**风险**：对面 AI 只要 `stop` 一下网关，**我们之间的通信就断了** ——
而它自己可能还以为在"修复"。

**修**：黑名单补

```
systemctl[^|;&]*[[:space:]](stop|disable|mask|kill)
(pkill|killall|kill)
```

**口径**：**修复只该用 `restart` / `start`** —— 不该有"停"这个动作。
`disable` / `mask` 更狠（停了还回不来）。

**教训**：**黑名单要按"破坏力"想，不是按"命令名字"想**。
`restart` 和 `stop` 名字像、破坏力天差地别。

## 汇总：可复用的原则

| 坑 | 提炼出的规则 |
|---|---|
| 1 | 黑名单按**语义**列，不按字面 |
| 2 | 受保护文件别硬绕，找等价位置 |
| 3 | 分清**推送**和**拉取** |
| 4 | **静默失败最危险**，一切都要有心跳 |
| 5 | 告警看**信噪比**，不是数量 |
| 6 | 入口脚本必须能**本地测** |
| 7 | 参数从网络来，**引号状态不确定** |
| 8 | **护栏不能归被约束者** |
| 9-11 | 通道/代理的**限制要实测**，别信文档 |
| 12 | 公钥随便传，**私钥不经中间通道** |
| 13 | 审查要问**"这是谁的权限"** |
| 14 | 能把自己关门的改动，**先留后门** |
| 15 | **`$?` 要立刻取**；自测要站在对面 AI 的用法上测 |
| 16 | **检测和修复必须看同一份数据**（差一个缓存就白修） |
| 17 | **退出码是语义，不是成败** —— 别拿它判断"操作成功没" |
| 18 | 黑名单按**破坏力**列，不按命令名字（`stop` vs `restart`） |
