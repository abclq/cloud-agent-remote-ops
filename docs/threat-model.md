# 🎯 威胁模型：沙盒里的私钥不是秘密

> 这一节决定后面所有设计。**先想清楚敌人在哪，再谈给多少权限。**

---

## 一句话

**你给云端 AI 的那把 SSH 私钥，住在一台你不拥有的机器上。**

所以它不是秘密 —— 它是**半公开凭据**。

---

## 具体威胁：谁看得见那把私钥

云端 AI 沙盒（Claude Code on the web、各家 Agent 平台、临时容器……）的典型形态：

| 项 | 现实 |
|---|---|
| 机器归谁 | **平台**，不归你 |
| 平台能不能读你文件 | **能**（那是它的机器、它的 hypervisor） |
| 沙盒活多久 | 会话级，随时回收 |
| 你能否审计平台 | ❌ 不能 |
| 私钥放哪 | 只能放沙盒里（否则 AI 用不了） |

结论：**你必须在「假设那把私钥已经泄露」的前提下设计。**

---

## 于是有两种错法

### 错法 A：给完整 shell

```
command= 不加 → 那把钥匙 = 一个完整的 SSH 登录
```

最坏情况：拿到私钥的人（或平台本身）可以

- 读你 `~/.ssh/`、`~/.hermes/shared/`、`.env`、token
- 写 `~/.ssh/authorized_keys` → **加自己的钥匙** → 持久化
- 横向摸你内网
- 走你的机器出去做别的事

**而且它自己都不需要恶意** —— AI 判断错、被提示注入、跑错命令，后果一样。

### 错法 B：给只读，但以为"只读 = 安全"

只读确实挡掉大部分破坏，但：

- 只读**看得到凭据** → 私钥、token、cookie 全暴露
- 只读也能**做探测** → 内网扫描、端口试探
- 一旦你哪天为了"让它能修"开了写 → 前面攒的所有认知瞬间失效

**只读是缓解，不是解决。**

---

## 我们的答案：三个约束同时成立

```
① 钥匙打不开 shell        → 只能跑一个入口脚本
② 入口只认具名动作        → 参数拼不出任意命令
③ 入口脚本 root 拥有只读  → 它改不掉自己的护栏
```

三条缺一不可：

- 只有 ① → 入口脚本本身如果有洞（比如 `eval "$1"`）就等于 shell
- 只有 ①② → 入口脚本归它所有的话，它能改掉入口
- 只有 ①③ → 没写权限，它就只是个只读探针，修不了东西

**①③ 由 sshd 保证（它碰不到），② 由我们自己的代码保证。**

---

## 一个常见的反驳

> 「但平台是可信公司啊，它不会偷我 key。」

可能不会。但威胁模型不评估"对方有多好"，只评估**"如果这条路径被打通，最坏是什么"**。

而且现实中被打通的路径往往是：

- 平台被入侵
- 沙盒里跑的**别人的**代码（多租户）
- AI 被提示注入，**主动**把私钥发出去
- 平台日志/备份里落了你的 key

这四条里，**没有一条需要平台"故意作恶"**。

---

## 那还能让 AI 干活吗？

能 —— 这正是本项目要解决的。

关键转变：**不要给它"一台服务器"，给它"几个动作"。**

```
❌ 给它 shell          → 它能做任何事
✅ 给它 status/verify/fix/exec → 它只能做你定义过的事
```

第 3 层 `exec` 看起来又像 shell 了 —— 所以它必须配**护栏 + 审计 + 提权链审查**（见
[护栏设计](guardrails.md) 和 [⚠️ 提权链审查](privilege-audit.md)）。

## 自检清单

上线前问自己：

- [ ] 我能不能接受**这把私钥明天就泄露**？
- [ ] 那把钥匙打不开 shell 吗？（`command=` 或 `ForceCommand`）
- [ ] 入口脚本**归 root** 吗？它能自己改掉入口吗？
- [ ] 入口接受的是**具名动作**，还是会拼字符串执行？
- [ ] 我审过**提权链**吗？（它写的文件，有 root 会执行吗？）
- [ ] 每次调用都有**审计日志**吗？
- [ ] 最坏情况下，它能碰到什么？（答案应该是：**到那个用户为止，碰不到 root**）

七条全 ✅ 才继续。有一条 ❌ 就先别开写权限。
