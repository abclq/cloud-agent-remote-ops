# 📣 告警与回执：怎么吵、吵完怎么收场

> 告警设计的目标不是"通知到"，是**"被正确的人正确对待"**。

---

## 三条铁律

1. **只有「能连上 + 有故障」才吵人**（见 [四态判定](detection-states.md)）
2. **同一个问题不重复吵**（指纹去重）
3. **吵完要等回执**，没人回就自己上

---

## 通道选择

### 先问一个问题

> **这条通道，人会看到吗？**

我们踩过的坑：**发出去 ≠ 被看到。**

| 通道 | 会看到吗 | 延迟 | 适合 |
|---|---|---|---|
| IM 推送（Telegram/Slack/企微） | ✅ 会（有提醒） | 秒级 | **告警首选** |
| 手机推送（Pushover/Bark） | ✅ 会 | 秒级 | 个人项目首选 |
| 邮件 | ⚠️ **看人** | 分钟～天 | **别当主通道** |
| 写文件 / 日志 | ❌ 不会 | — | 只做留痕 |
| Web 面板 | ❌ 不会 | — | 只做查证 |

### 🔴 我们的真实教训：邮件不是推送

我们一开始用邮件做"派活 + 告警"通道，本机发、对面收。**跑通了，也真的回信了。**

但后来翻对面 AI 的会话记录才发现：

```
15:12:42  用户:  看看邮箱
15:14:10  AI:    有一封要处理：本机 23:05 发来的邮件…
```

**它是"被问了才去读"** —— 邮件**不会主动唤醒它**。

于是我们发的三封邮件，它**一封都没看到**。

**教训**：邮件是**拉取**模型（poll），不是**推送**（push）。
用邮件做"实时派活/告警"，等于把消息扔进一个"下次被想起来才会打开的抽屉"。

**要用可以，但必须配一个定时拉取**，否则就是白发。

### 建议

```
主通道：IM 推送        ← 秒级、会响、能带按钮
副通道：邮件          ← 只做留痕和"长文详情"
落盘：  state/*.json  ← 状态机持久化（不是通知）
```

## 告警内容模板

**一条好的告警 = 现象 + 判断 + 行动建议**

### 坏例子

```
ERROR: example.service inactive
```

问题：不知道要不要管、不知道是什么服务、不知道下一步。

### 好例子

```
⚠️ example.service 停了

· 这是什么：常驻服务（应该一直跑）
· 现在状态：inactive (dead)
· 上次正常：12 分钟前
· 影响：xxxx 功能不可用

👉 30 分钟内没回应，我会自己尝试重启。
```

**四个要素**：**是什么 / 现在怎样 / 什么时候开始的 / 要不要管**。

## 指纹去重

### 为什么

「磁盘 85%」如果每 10 分钟报一次，你一天收 144 条 —— **然后你就开始无视它了**。

### 怎么做

```python
def fingerprint(problems):
    # 只取"问题集合"本身，不含时间戳
    key = sorted(
        f"{p['kind']}:{p['name']}" for p in problems
    )
    return hashlib.sha256("\n".join(key).encode()).hexdigest()[:16]
```

⚠️ **不要**把 `checked_at` 之类的易变字段算进指纹 —— 那样每次都不一样，等于没去重。

### 效果

| 情况 | 提示吗 |
|---|---|
| 同一个问题，第二次检查 | ❌ 不提示 |
| 问题消失了 | ❌ 不提示（或提示"已恢复"） |
| 问题**变了**（多了一个/换了一个） | ✅ 提示 |
| 问题消失后又**复发** | ✅ 提示（指纹从 A→无→A） |

## 回执机制

### 流程

```
检出问题
   │
   ├─ 发告警（带"我会自己修"的预告）
   │
   ├─ 起一个计时器（默认 30 分钟）
   │
   ├─ 30 分钟内有人回执？
   │     ├─ 是 → 人接手，哨兵退让 ✅
   │     └─ 否 → 它自己上手修 🔧
   │
   └─ 修完发结果（成功 / 失败 / 修了但还是不对）
```

### 回执怎么收

最简单的做法：**看告警通道的回复**。

```python
# 伪代码
if now > receipt_deadline and not receipt_received:
    result = self_heal(problems)
    notify(f"🔧 没等到回执，我自己修了：{result.summary}")
```

### 为什么"退让"很重要

如果人和 AI **同时**动手修同一个东西 → 互相踩。

**规则**：人一回执，哨兵就停手等下一轮。

## 通知去重状态机

```python
class Notifier:
    def maybe_notify(self, state, fingerprint, detail):
        # 状态没变 + 指纹没变 → 闭嘴
        if state == self.last_state and fingerprint == self.last_fp:
            return
        # 状态变了 或 指纹变了 → 说话
        self.send(state, detail)
        self.last_state, self.last_fp = state, fingerprint
```

**这一个函数就能消掉 90% 的告警噪音。**

## 静默期

维护窗口内别吵：

```bash
# ~/.config/sentinel/quiet-hours
22:00-08:00        # 夜里只报 P0
```

或者干脆：**夜里只自修，不通知**，早上汇总一条。

```
🌙 夜间汇总（22:00-08:00）
   · 02:14  example.service 停了 → 已自动重启 ✅
   · 05:30  磁盘 /data 92% → 只报告，未处理
```

**这比半夜把你叫起来强得多。**

---

## 自修之后也要说

**修完了必须发一条**，否则你不知道它动过手。

```
🔧 自动修复报告
· 问题：example.service inactive
· 动作：systemctl --user restart example.service
· 结果：✅ 已恢复（active）
· 耗时：3 秒
```

**失败了更要说**：

```
🔴 自动修复失败
· 问题：example.service inactive
· 试了：restart → 5 秒后又死了
· 判断：不是"没启动"，是"起不来" → 要看日志
· 日志最后 5 行：…
· 需要你：看一眼配置
```

**"我试过了但不行"比"服务挂了"有用得多。**

## 通道失效也要监控

**哨兵自己也会挂。** 如果哨兵挂了，你就永远收不到告警了。

**做法**：让哨兵写**心跳**，再用**另一条路**检查心跳新鲜度。

⚠️ 哨兵在云端，它写的心跳文件也在云端 —— 本机 cron 读不到。心跳得**落到本机**：
最省事的是把每轮 `verify` 调用本身当心跳（入口脚本收到 `verify` 时写一个时间戳），或者用外部心跳服务。

```bash
# 入口脚本收到 verify 时顺手写（本机）：
date -Is > /home/agent-ops/.local/state/sentinel.heartbeat

# 本机 cron 每 10 分钟查：
if [ $(( $(date +%s) - $(stat -c %Y /home/agent-ops/.local/state/sentinel.heartbeat) )) -gt 1800 ]; then
    echo "⚠️ 哨兵 30 分钟没动了"
fi
```

**我们踩过这个坑**：哨兵的邮件脚本静默失败（`exit 0`），
结果**连续几天什么都没报** —— 看起来"一切正常"，实际是**哨兵死了**。

**静默失败是最危险的失败。** 任何脚本都要：

- 成功 → 写心跳
- 失败 → **非零退出 + 写日志**（绝不静默 `exit 0`）

## 检查清单

- [ ] 主通道是**推送**（不是拉取）吗？
- [ ] 告警文案有"要不要管"的判断吗？
- [ ] 同一问题**指纹去重**了吗？
- [ ] 有**回执机制**吗？没人回会自修吗？
- [ ] 人回执后哨兵会**退让**吗？
- [ ] 有**静默期**吗？
- [ ] 自修**成功和失败都通知**吗？
- [ ] 哨兵自己有**心跳**吗？心跳停了有人发现吗？
- [ ] 脚本失败时是**静默 exit 0** 还是明确报错？
